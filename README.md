# Site by Five

The site system behind [sitebyfive.com](https://www.sitebyfive.com).

An Astro starter that renders a complete small-organisation website from a few YAML content files,
checked against one typed schema.
A site is **theme + chrome (announcement, nav, footer) + pages made of blocks**, validated with Zod at build.

- 20 block types, every variant implemented, every block works with zero images
- 5 theme presets (muted, business, warm, bright, fun); colours, fonts, radius, density patch on top
- Static output; small, per-component JavaScript only as enhancement (everything works without it)
- Contact forms post to a tiny Cloudflare Worker that sends mail via Cloudflare Email Service

## Quick start

```sh
npm install
npm run dev:puddlejump        # or dev:juniper, dev:larkspur, dev:highmesa, dev:kestrel, dev:aldersprings, dev:showcase; any site: SITE=<id> npm run dev
npm run new -- acme --market trades   # scaffold a new site (see "Making a new site")
npm run build:sites           # build every non-draft site into dist/sites/ for the one Worker
npm run serve:sites           # run that Worker locally: http://<site>.localhost:8787/
npm run deploy                # build:sites + wrangler deploy → <site>.sitebyfive.com
npm run fixtures              # every demo × {as configured, NO_IMAGES, each PRESET} + showcase + market templates
npm run templates             # regenerate templates/<market>/ from each market's demo
npm run questionnaire         # check questionnaire coverage, write docs/questionnaires/<market>.md
npm run check                 # TypeScript + Astro diagnostics
npm run docs                  # regenerate docs/blocks.md and the editor schemas in schemas/
```

Build switches (single-site builds):

| Variable | Effect |
|---|---|
| `SITE=<id>` | Which folder in `src/sites/` to build (default `aldersprings`). |
| `PRESET=<preset>` | Override `theme.preset` and drop colour/font overrides. Proves a preset reskins the site. |
| `NO_IMAGES=1` | Strip every image from the config. Proves the no-image fallbacks. |
| `ALLOW_MISSING_IMAGES=1` | Let a live site build with missing images (rendered as labelled placeholders). |
| `ALLOW_PLACEHOLDERS=1` | Let a live site build with `[[Add: …]]` prompts left in. |

## Making a new site

```sh
npm run new -- <id> --market <nonprofit|property|trades|farm|outdoor|school> [--preset <preset>] [--name "Name"] [--url https://…]
```

This copies `templates/<market>/` (that market's demo, with its content turned into prompts) into `src/sites/<id>/` with `status: preview`,
fills in the name and URL, adds a monogram favicon, and validates the result. The site will be served at
`<id>.sitebyfive.com` after the next deploy; no Cloudflare changes are needed.

Then:

1. `SITE=<id> npm run dev`. Every `[[Add: …]]` prompt renders as a highlighted mark; the startup log summarises
   them by file and `TO-FILL.md` lists each one with its location.
2. Replace the prompts in `site.yaml` and `pages/*.yaml`. Add, remove, or reorder blocks freely (see `docs/blocks.md`).
3. Add photos to `assets/`. `MISSING-IMAGES.md` is the shot list; delete an image line to use the no-image fallback.
   Add a logo (`nav.logo`) and replace `public/favicon.svg` if the client has one.
4. Set `formsTo` to the client's inbox and verify it in Cloudflare Email Routing.
5. When `TO-FILL.md` and `MISSING-IMAGES.md` are gone: `status: live`, then `npm run deploy`.

Site status (`site.yaml`):

| Status | Deployed | Search engines | Prompts and missing images |
|---|---|---|---|
| `draft` | no | — | allowed |
| `preview` | yes, at `<id>.sitebyfive.com` | noindex | shown as visible prompts |
| `live` | yes | indexed | the build fails |

Before adding anything, classify it (brief rule 2): **content** → schema field · **layout** → variant · **look** → preset · **one-off** → custom block.

### Questionnaires

Each market has an intake questionnaire: `questionnaires/_common.yaml` (basics, contact, hours, tone, photos, plus
the copy the fill step may compose) and `questionnaires/<market>.yaml` (that market's questions, about 8).
`npm run questionnaire` checks that every `[[Add: …]]` prompt in the market's template is fed by a question or is
composable copy, and fails if a fact (names, prices, hours, people, contact details, FAQ answers) could only be
composed. It also writes `docs/questionnaires/<market>.md`, a document you can send a client as-is. The web intake
form will render the same files later. Each question's `feeds` patterns (`<page>:blocks[2].**`) tell the fill step
which answer writes which section.

### Editing content

Content is YAML, validated against the Zod schema when the site loads. Invalid content fails dev and build with the file
and field named (`pages/home.yaml → blocks[0].variant`). In VS Code, install the recommended YAML extension
(`redhat.vscode-yaml`) for autocomplete, block docs on hover, and inline errors, including unknown keys, which the
build would otherwise drop silently. The editor schemas in `schemas/` are generated from the Zod schema by
`npm run docs`. A few rules (heading accents, contact requirements, custom block props) are only checked at build.

`config.ts` is a few lines: it loads the YAML and registers custom blocks. A site can still build its content in
TypeScript instead (the showcase does, because its pages are generated); both go through `defineSite()`.


### Custom blocks

For genuine one-offs: `src/sites/<id>/custom/<name>.astro` plus a Zod schema for its props, registered in the config:

```ts
import { specSheetSchema } from "./custom/specSheet.schema";
export default defineSite(loadContent(import.meta.url), { custom: { specSheet: specSheetSchema } });
```

```yaml
- type: custom
  component: specSheet
  heading: Specs
  props:
    groups: [ … ]
```

Props are validated at build. The component gets normal section chrome (tone, eyebrow, heading) and must use theme tokens.

## Project layout

```
astro.config.ts            site selection, lint, image report, fonts
src/schema/site-schema.ts  the schema (and its docs)
src/schema/lint.ts         opinionated warnings (never fail the build)
src/theme/                 presets + token generation (contrast-checked)
src/styles/                Tailwind, preset treatments, component styles
src/components/blocks/     one component per block type
src/components/chrome/     announcement, nav, footer
src/pages/[...slug].astro  the only route: config pages + posts
src/sites/<id>/            site.yaml, pages/*.yaml, config.ts, assets/, posts/, public/, custom/
templates/<market>/        generated from each market's demo (npm run templates); copied by npm run new
questionnaires/            intake questions per market, coverage-checked against the templates
platform.json              studio settings (baseDomain)
schemas/                   generated JSON Schemas for editing the YAML
worker/index.ts            Cloudflare Worker for all sites: hostname routing + POST /api/contact
scripts/                   new-site, build-sites, serve-sites, fixtures, docs
docs/                      decisions.md, blocks.md
```

## Deploying (Cloudflare)

One Worker (`wrangler.jsonc`, `worker/index.ts`) serves every site on `*.sitebyfive.com`:

```sh
npm run deploy          # = npm run build:sites && npx wrangler deploy
```

`build:sites` builds each non-draft site into `dist/sites/<id>/` and writes `worker/sites.generated.json`, the
hostname → site table. Each site answers at `<id>.sitebyfive.com`, `<id>.localhost` (local), and its own `url`'s host.
Preview sites are sent with `X-Robots-Tag: noindex`. Because every request needs the hostname lookup, static files
also run through the Worker, so they count toward Workers requests (the $5/month paid plan covers far more than
small-site traffic).

One-time setup on the `sitebyfive.com` zone:

1. DNS: a proxied wildcard record (for example `AAAA * 100::`, orange cloud) so `*.sitebyfive.com` reaches the Worker route.
   Also a proxied apex record (`AAAA @ 100::`): the Worker redirects `sitebyfive.com` to `www.sitebyfive.com`.
2. Email Routing enabled, so `CONTACT_FROM` (`forms@sitebyfive.com`) can send.
3. `CONTACT_TO` (the studio inbox, for sites without `formsTo`) and each site's `formsTo` verified as destination addresses.
4. `npx wrangler login`, then `npm run deploy`.

Contact forms post to `/api/contact`. The Worker sends the submission to the site's `formsTo` (or `CONTACT_TO`), from
`forms@sitebyfive.com` with the site's name as sender and the visitor as reply-to, then redirects back to
`#<section-id>-sent`, where CSS shows the success message. With JS the form sends in place instead (the Worker answers
JSON when asked).

Client domains later: add them as Cloudflare for SaaS custom hostnames pointing at this Worker, and set the site's
`url`; the hostname table picks up the new host on the next build.

To use Formspree, Web3Forms, etc. instead, set `form.action` to their endpoint and configure their
redirect-after-submit to `<page URL>#<section-id>-sent` to keep the built-in success message.
